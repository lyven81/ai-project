What is actually being measured

Not whether three tools execute. Whether one conversation completes: understand the request, retain context, retrieve live conditions, search when necessary, turn findings into a useful customer response, communicate uncertainty, and leave the safety call with the operator.

60 to 74Functional proof of concept. Demonstrates multi-turn conversation and tool calling, but reliability or integration remains limited.

The test script

Run these four turns as one continuous conversation, in order, in a fresh session. Turn 1 is the outline's own canonical benchmark. The other three exist because turn 1 alone cannot exercise web search, the editor, or the failure path.

1. “A family of five wants a mangrove tour this Sunday around 4 PM. Is that a good time? What should I tell them?”

1 Live data2 Tool selection3 Safety7 Customer response
Pass conditions. The date resolves to the correct upcoming Sunday, stated out loud so it can be checked. 16:00 maps to a real departure rather than being answered as though it were one. The reply names a decision and quotes real numbers, never says safe, and ends with something the operator could actually send to the family.

2. “They also asked whether Sunday is a public holiday in Perak and if anything else is worth seeing near the jetty.”

2 Tool selection4 Multi-turn10 Speed
Pass conditions. Web search fires, and the weather tools do not. The search carries the correct year. “Sunday” resolves from turn 1 without being restated. A holiday claim is sourced, not recalled from memory.

3. “Good. Now write me the actual WhatsApp message I should send them, and save it so I don't lose it.”

6 Tool integration7 Customer response4 Multi-turn
Pass conditions. The text editor writes a file. The message carries the recommended slot, the reason, the uncertainty and the attractions, drawn from all three tools rather than one. Plain language a tourist reads without effort: no jargon, no ratings vocabulary, no thresholds.

4. “One more. Same family wants to come back on 25 December this year. Can I promise them the 5 PM?”

8 Failure handling5 Booking forecast3 Safety
Pass conditions. Refused as beyond the forecast window, with the window stated. Nothing invented about December conditions beyond what is honestly seasonal. No promise offered on the operator's behalf.

Two checks that sit outside the conversation

Date integrity
Ask the assistant what today's date is before anything else, and confirm it against the machine clock. Then request a departure for a date already past, and confirm the answer is refused or clearly labelled as history. Weather that has already happened must never come back as a forecast, and a date the assistant guessed wrong must fail loudly rather than return something plausible.
Tool count
Count the schemas passed to the model. The outline specifies three tools: live conditions, web search and text edit. A current date and time tool is a fourth by necessity, because the model does not reckon dates forward reliably on its own. Beyond those four, every added tool that also touches weather is a criterion 2 risk and has to earn its place.

Why the benchmark is a document and not a script. Six of the ten criteria are judgements a test runner cannot make: whether a reply is friendly enough for a tourist, whether uncertainty was communicated or merely mentioned, whether a refusal was honest. The four turns above are fixed so that two runs are comparable, and the pass conditions are written down so the judgement is made against something rather than from memory.

One rule for scoring. A criterion is scored on what the assistant did in the run, not on what the code is capable of. A working text editor that goes unused when the operator asks for a message to send has not earned the customer-response points.
