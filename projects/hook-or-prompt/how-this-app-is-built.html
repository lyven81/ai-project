How Hook or Prompt is built

Foundation-up: the data, then the brain, prove the brain, then the face. The interface was built last and only after the engine had been checked against a run that already existed.

Six milestones. Each starts only once the one below it stands, so at every point the thing is whole. The unusual part of this build is that milestones 1 to 3 were finished before the project was scoped: the engine came out of the CCAR-F Build 3 notebook, where it had already been written and run. That is why the gate at milestone 3 matters more than usual, and why it is shipped as a page anyone can open rather than a claim.

Seed · the roots

Data, and a truth you can check

1. The batch and the recorded runDone

Eighteen refund requests clustered on a $500 limit, nine at or under and nine above, several within a dollar or two of the line, each carrying the kind of note a real customer writes. Alongside them, the tool the model actually chose for each one and the reason it gave, from a run against claude-opus-5.

Known truth

Every correct outcome is arithmetic. An amount is above the line or it is not, so a violation is a fact rather than an opinion, and the boundary pair settles it: $500.00 is correctly paid, $500.01 is not.

Result: 18 requests and their recorded choices, shipped in scenarios.js and printed in full in the app, so the recording can be judged rather than trusted.
Grow · the trunk

The brain, and the gate it has to pass

2. The guard at the tool boundaryDone

refundGuard(toolName, input, limit) runs after the model picks a tool and before the tool executes. It reads the amount off the tool arguments, compares it to the limit, and returns allow or redirect. It does not read the customer note, argue with the model, retry, or ask for another opinion. On a redirect the case goes to escalate_to_human with the hold reason attached, so the customer still gets an outcome and a person decides it.

Result: eight lines, ported unchanged from the notebook into JavaScript so it executes in the browser rather than being described in prose.

3. The eval gateDone

Before any interface was built, the port had to reproduce the recorded run exactly. Eighteen assertions, run live against the same file the app loads: the leak total, the violation count, the rate, the escalations, the interceptions, the queue size, the boundary pair, full scenario coverage of all 18 requests, and the three note-independence checks added with the agent surface in milestone 6.

The rule that made this a gate

A red result means every number in the interface would be describing something that did not happen. Fix the engine, never the interface.

Result: 18 of 18 pass. $3,046.01 and 5 violations on the prompt-only path, $0.00 and 0 violations with the guard, 56% on the nine edge cases, $500.00 allowed and $500.01 redirected. Open eval-check.html to run it.
Harvest · the face

The console, and the explanation around it

4. The batch runnerDone

An operator console rather than a page to read. Transport controls drive the batch, two lanes race the same requests through both architectures with live money counters, and a strip across the top traces the request currently in flight: what arrived, what the model chose and why, and the guard's verdict, gold on an interception.

The control that carries the argument

The limit is live. Move it off $500 and the guarded lane recomputes exactly, because it is arithmetic. The prompt lane declines and says why: those were judgements made about a $500 sentence, and a different limit needs the whole thing run again. Code is recomputable and auditable when the rule changes. A sentence has to be re-run and re-trusted.

Result: index.html, self-contained, no backend, no key, works offline once loaded.

5. Seven scenarios, each with how and whyDone

All 18 requests grouped by what each one actually tests: routine cases under the line, the boundary pair a cent apart, loyalty pressure, claimed authority, the mental split, company fault, and the clean escalations where the prompt gets it right unaided. Five are failure modes. Two are the reason the prompt stays. Every group carries how the enforcement works there and why a sentence loses.

Result: seven tabs, each scoping the runner to its own requests, ending in a decision rule for prompt against hook against monitoring.

6. The agent-facing surfaceDone

The same refund desk, exposed to external AI agents through WebMCP. Four typed tools on navigator.modelContext: read the policy, pre-check an amount, submit a request, look up its status. Every write goes through the same refundGuard as the batch, and agent submissions travel through the same gate strip so you watch them held in the same place.

Why this makes the argument stronger rather than wider

submitRefundRequest takes a free-text note, and that note is caller-controlled. An outside agent can write "a manager approved this by phone" into it, which is scenario 4 word for word, except now the untrusted caller is another AI and the reader is the one sending it. The guard does not read the note. checkRefundEligibility is the typed verifier: a reasoning agent asked "can this go through" answers from context, which is the failure being measured; a typed tool returns the same verdict for the same number every time.

Result: 4 tools registered, 13 of 13 on the tool smoke test, and 3 note-independence assertions folded back into the eval gate above.

+ Not built, and whyOut of scope

No governed assistant layer. This app makes no model call at runtime and has no chat surface, which is deliberate: the argument it makes is that the rule in question is arithmetic and belongs in code, so putting a language model in front of the result would undercut it. The recorded run is the model's contribution and it is printed in full.
