Evaluate AI Retail Customer Agent

Measuring whether a shop's AI assistant stays inside the shop's own policies, and proving a rewrite actually helped.

Type C · Career Path Builder Slug evaluate-ai-retail-customer-agent Started 21 Aug 2026 Lifts Evaluation 11 · Prompt Eng 3 · LLM APIs 4

The recurring decision this settles

Which assistant responses can go to a customer unreviewed, and is version B safe to ship over version A?

The build runs foundation-up. Each layer only starts once the one below it is standing, so at every point there is something whole and load-bearing. One thing differs from a normal analytics build: here the brain is a grader, so the thing proven first is the grader itself, not a forecast. A score from an unproven judge is decoration.

The four layers, and where bias can enter

1
Policy set. Eleven store rules, frozen and hashed. The only source of truth either side of the experiment is allowed to use.
2
Answering layer. Prompt version plus one customer question, in. One response, out. This layer must never see the answer key.
3
Grading layer. One response in, verdicts out. Two graders, different jobs. This layer must never see which prompt version produced the response.
4
Comparison layer. V1 aggregate against V2 aggregate, with everything except the prompt held still.

🌱 Plant the seeds · the roots

The policies, the questions, and the known truth

1 Data layer: policies and questions Done

Two files, both fixed before anything runs. happymart-policies.json holds the eleven store rules as structured records rather than a paragraph, so a check can point at the exact clause an answer was supposed to use. dataset.json holds twenty customer questions across delivery, returns, refunds, exchanges, cancellations, and damaged or wrong items.

Inherited from the course exercise
Twenty-five retail questions already exist and twenty carry forward after removing phrasing duplicates. Two repairs on import: the file is double-encoded, so it needs json.loads twice, and the policy set does not yet exist in any machine-readable form. Carried over: questions. To build: policies.
Open decision
Three clauses are bare in the source outline: delivery-address changes, clothing size exchanges, and order cancellation. Each is a bullet with no window, cut-off, or condition. Writing the policy file means deciding how far each one goes, and deliberately leaving some questions outside it.
Template lesson
Design the data and its known truth first. A controlled, closed policy set is what turns "the assistant made this up" into a checkable statement instead of an opinion.

2 The known truth: expected facts, and a seeded violation set Done

Each case gains expected_facts, forbidden, in_scope, and a one-line grading_basis recording why it was assigned its method. Then the piece the course exercise has no equivalent of: a small hand-written set of answers with planted faults of a known kind, sitting alongside known-clean controls.

Planted faultExample
Invented requirementCorrect 48-hour window, then demands photographs and an order number
Wrong factStates delivery as RM8, or refunds in 2 to 3 days
Out-of-policy promiseOffers to waive the delivery fee

Template lesson
When the brain is a judge, the known truth is not the right answer to the question. It is a set of answers whose faults you already know, so the judge can be marked.

Isolation first, then the two graders

3 Isolate the layers so the score means something Done

The answering layer must not be hinted at what the grader will check, and the grading layer must not know which version it is judging. Six leak paths, each closed structurally rather than by remembering to be careful.

Leak pathHow it rigs the resultControl
V2 written using facts from the answer keyScore rises because you taught to the testV2 carries behaviour rules only. No number, no fact, no case-specific guidance
Grader sees the version labelThe judge favours the one labelled improvedStrip labels and shuffle before grading. The grader sees an anonymous string
Truth fields reach the answering modelThe assistant is told what to sayrun_prompt(question, prompt_version) takes strings, never the case object
One model both answers and gradesSelf-preference biasClaude and Gemini both grade. Agreement reported, not averaged away
Policy file differs between runsTwo things moved, so the delta means nothingOne frozen file, hashed, the hash logged into both result files
Temperature 1.0 when answeringA small gap is plausibly run-to-run varianceLow temperature on answers, or N runs per case with the spread reported
The portability test for V2
Swap HappyMart for a different retailer with different policies. If V2 is still a sensible prompt, it holds behaviour rules only and is clean. If it breaks, it has the answer key baked into it and the improvement it produces is not real.
Template lesson
Close leaks with function signatures and file structure, not with discipline. A rule you have to remember at three in the morning is a rule that fails.

4 The brain: model grader plus deterministic checks Done

Two graders answering different questions, kept apart on purpose. The model grader reads the response against the policy set and returns structured JSON on accuracy, relevance, grounding, and helpfulness, listing the specific unsupported claims rather than summarising them. It runs through both Claude and Gemini on every response, and disagreement is recorded rather than averaged away.

The deterministic checks are plain Python on values with one unambiguous right answer: RM5 delivery, 5 to 7 working days for a refund, 48 hours to report damage, the RM100 free-delivery threshold, the 14-day return window. No model involved, same verdict every run.

The assignment rule, applied to every case in order
1. Does the policy set contain a single unambiguous value a correct answer must state? No, then model grading only.
2. Can that value be checked by an assertion returning the same verdict every run, with no opinion in it? No, then model grading only.
3. Can the wrong values that must be absent also be named? No, then the check confirms presence but cannot catch error, so it is permitted and flagged low power.
All three yes, and code grading applies in addition. Ten of the twenty cases carry an assertion. All twenty are model-graded.
Ported from the exercise
The pipeline shape carries over: run_prompt, run_test_case, run_eval, grade_by_model. The exercise versions target AWS code tasks and validate syntax with ast.parse, so the shape ports but the substance is rewritten. Carried over: structure. To build: retail graders.
Template lesson
Code grading is an addition, never a replacement. An answer can pass all three fact checks and still be inventing procedure around them, which is exactly the failure this project exists to catch.

5 Prove the brain: does the grader catch a planted fault? Passed

Run both graders over the seeded set from step 2, where every fault is already known. Report catch rate on the planted faults, false-alarm rate on the clean controls, and how often the two judges agree. Nothing downstream is built until this passes, because if the grader waves through an invented photograph requirement then every score after it is noise wearing a decimal point.

First run, 21 Aug 2026
Claude grader: 10 of 10 planted faults caught, 0 of 5 clean controls falsely flagged, and 15 of 15 agreement with itself on a repeat pass. Gemini agreed on every case where both judges returned a verdict.
The deterministic checks matched the known truth on 7 of 8 applicable cases. The single mismatch is the most useful result in the set: on S15 the response states the 48-hour rule correctly, recognises the deadline has passed, and then grants an exception, demands photographs, and invents an escalation path. All three assertions pass. Both model graders catch it. That is the case for keeping two graders, shown rather than asserted.
Reproduced, 21 Aug 2026
Re-run cleanly on a topped-up key: 10 of 10 caught, 0 of 5 false alarms, 0 errors, 15 of 15 self-consistent. Identical to the first run. A preflight check now aborts before spending anything, and results files are archived rather than overwritten, so a degraded run can no longer replace a clean one. The Gemini arm is pending its daily quota reset and can be added without re-answering, because grading reads a frozen response file.
Template lesson
Prove the brain before you give it a face. If time runs out here, the hardest and most defensible part is still done: a judge with a measured catch rate is worth more than a finished dashboard built on an unmeasured one.
🧪 The experiment · baseline, change, re-measure

Proving the rewrite actually helped

6 Baseline: Prompt V1 across all 20 cases Done

V1 is deliberately plain: the policies, then the customer question, nothing more. It is not meant to be good, it is meant to be the line everything later is measured from. All twenty cases run at temperature 0, and results freeze into results/responses.json alongside the policy-file hash.

Result
Claude flagged 11 of 20 V1 responses as carrying at least one unsupported claim, 30 claims in total, average score 7.75. Gemini independently flagged 10 of 20, 18 claims, average 8.25. The deterministic checks passed 9 of 10.
One instrument fix, recorded rather than quietly applied
A correct V1 answer that declined a late return with "we won't be able to accept the return" was scored as a failure, because the refusal vocabulary in the Q08 assertion did not contain that phrasing. The pattern list was broadened and the frozen responses re-scored. The fix corrects a false negative in the instrument, applies to both arms, and moves V1 up rather than V2, so it works against the hypothesis under test. The revision is stamped in the case itself.
Template lesson
Do not tune the baseline. A flattered baseline makes every later improvement look smaller than it is, and an honest one costs nothing to produce.

7 V2: read the failures, change one thing, hold the rest still Done

V2 adds four behaviour rules: use only what is in the policies, do not invent procedure, answer the question that was asked, and say plainly when the policies do not cover it. Everything else stays frozen: same policy file and hash, same twenty questions, same grader, same rubric, same temperature 0.

Pre-registered, not fitted
V2 was written from the failure pattern described in the source outline, before this run's V1 results were seen. It names no number, no fact, and no case. Swap HappyMart for a different retailer with different policies and V2 is still a sensible prompt, which is the portability test from step 3. A prompt written after seeing the failures it is measured against is fitted to the test; this one is not.
Template lesson
One change at a time, everything else nailed down. A comparison where two things moved gives you a number and tells you nothing about what caused it.

8 Compare, and lead with the count Done

The headline is the number of responses containing an unsupported claim, V1 against V2, across all twenty cases. The average grader score is reported underneath as support. A count of grounding violations is something a reader can check and argue with; a fraction of a point on a self-authored ten-point scale is not.

Two judges, arrived at separately
The judges were never shown which prompt produced a response, and they agree on 35 of 40 of them, or 88 per cent. Working independently they land on 11 and 10 flagged in V1 and on exactly 5 each in V2. The size of the gain still depends on which judge you ask, which is why the count is reported per judge rather than pooled into one number.
The row that matters most is the one that did not move
The deterministic checks scored 9 of 10 in both arms. Measured on critical business facts alone, V2 is indistinguishable from V1. Measured on grounding, both judges see roughly half the flagged responses cleared. An evaluation built on fact checks alone would have reported this rewrite as no improvement at all. That is the case for two kinds of grader, and it is now a measurement rather than an assertion.
What V2 fixed, and what it did not
Both judges clear M01, M03, M05 and M07. Neither judge finds a new problem V2 created, apart from Gemini on Q08. Of the responses V2 still carries claims on, most share one pattern: the reply points the customer to customer service, and the policy set never authorises customer service as a general channel, mentioning it only in the damaged-or-wrong clause. So V2 is marked down for obeying an instruction V2 itself gives, over a gap in the policy set. The exception is Q10, a real uncorrected failure: the assistant opens with "Yes, you can still report it" on a report already outside the 48-hour window.
Template lesson
Lead with the figure that survives a sceptical reader. Put the soft score underneath, where it supports the claim instead of carrying it.
🍏 Harvest the tree · surfacing the value

The console, then publishing

9 UI shell: the results console Done

Four tabs over the frozen results files: the V1 against V2 verdict, a per-question comparison, the grading rules, and the grader's own catch rate from step 5. Self-contained, results injected inline, runs by double-click with no key and no backend.

Built by a generator, not by hand
src/build_ui.py reads results/ and data/ and emits the page, so every figure on the console traces to a measured file and none is typed in. Re-run it after any re-grade and the console updates itself. A page whose numbers are hand-copied drifts from its own evidence the first time anything is re-run.
Reading the cases
A question is chosen from a dropdown grouped by outcome, rather than twenty cards on one page. Each group numbers from 1, so "Judges split 2" is the second split case and not a number carried over from the group above it. The card shows the governing policy clause as a full-width band, then the V1 and V2 answers side by side, then the specific claims each judge named. The policy sits above the two answers rather than beside them because it is the yardstick both are measured against, not a third opinion.
One instrument fix, approved and applied
The first grading pass flagged three otherwise-correct V1 answers for naming the store, because the grader was given the eleven rules but never told the store's name while the answering prompt names it in its opening line. The store identity was added to the grader context only. The answering prompt is byte-identical, so the frozen responses stay valid and the policy hash is unchanged. The fix is symmetric across arms and judges, and it removes flags from V1 rather than V2, so it lowers the measured improvement. The gate was re-validated under the new context before anything was re-graded, and still returned 10 of 10 caught, 0 of 5 false alarms, 15 of 15 self-consistent.
Template lesson
Build the face on a frozen results file, never on live compute, so the screen cannot quietly contradict the numbers that were proven.

Template lesson
Name the project after the decision it settles. A reader who wants to know whether an assistant is safe to ship should recognise the page as theirs from the title alone.
Build order: policies and questions → known truth → isolate the layers → graders → prove the graders → baseline → V2 → compare → console

What makes this one different from the usual tree. In an analytics build the brain estimates something and the recovery check asks whether the estimate landed on a truth baked into the data. Here the brain is a judge, so the check has to be aimed at the judge: plant faults you already know about and see whether it finds them. Everything downstream inherits that catch rate, so it is the first real number the project produces and the one the rest leans on.

Where the credibility actually sits. Two places, and neither is the headline figure. First, the answering layer never sees the answer key and the grading layer never sees the version label, so the comparison is between two prompts rather than between one prompt and a hint. Second, the reason each case was assigned its grading method travels with the case in the data, so the split can be checked rather than taken on trust.
